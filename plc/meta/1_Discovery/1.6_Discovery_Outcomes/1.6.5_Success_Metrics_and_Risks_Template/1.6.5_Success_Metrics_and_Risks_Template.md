# PLC_META — 1.6.5 Success Metrics & Risks Template

## Purpose

Provide a standard way to define:

- **Short-term success metrics** for PLC_2/3 (Solution & Planning), and
- The **top risks / assumptions** that must be validated next.

## Success Metrics (Examples)

Each product instance must define 3–7 concrete signals that indicate:

> “This seems to be working in the real world.”

Typical patterns:

- **Design partners / early adopters**
  - Number and type of organizations using the product in real scenarios.

- **Real-world usage**
  - Number of projects, runs, deployments, or workflows executed via the product.

- **Commercial signals**
  - Paying customers, pilots, renewals, upgrades, or strong pipeline.

- **Strategic signals**
  - Case studies, references, talks, co-marketing with platforms/partners.

Metrics should be **countable** and **verifiable**, even if the target values are modest at first.

## Risks & Assumptions

Each product instance must list **3–5 key risks or assumptions** that will be specifically targeted in PLC_2/3, e.g.:

- Adoption friction (complexity, required skills, change management).
- Platform/vendor evolution closing the differentiation gap.
- Regulatory / security concerns blocking certain deployment models.
- Execution bandwidth (can we actually build + sell + support this?).

These should be written as **statements to test**, not generic fears.

## Product-specific file requirements

Each `1.6.5_*.md` file must include:

1. A short list of **success metrics** for PLC_2/3 (with rough target numbers or ranges).
2. A bullet list of the **top 3–5 risks / assumptions** to validate next.
3. Optional: a note on how these feed into planning for PLC_2 (Solution) and PLC_3 (Roadmap & Planning).
