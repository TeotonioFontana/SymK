# 2.0.4 — Layer-Boundary Analysis

**Status:** Questioned

## Purpose

Define the boundary among SymK, derived projects, organizations, implementations, and operational deployments. The objective is to determine where a commitment belongs, not to finalize every commitment.

## Proposed layers

| Layer | Owns | Must not silently own |
|---|---|---|
| SymK Constitution | Universal purpose, epistemic constraints, minimal participant account, inheritance | Domain ontology, product policy, implementation choices |
| SymK foundational corpus | Arguments, governed concepts, principles, methods, standards | Ratified authority merely by publication |
| Derived-project Constitution | Domain axioms, domain Ontology and Logic, specialization of inherited commitments | Redefinition or weakening of SymK without challenge |
| Engineering Charter | Design obligations translating constitutional commitments | Philosophical claims created by architecture |
| Specification and architecture | Testable structures, interfaces, protocols, models | Silent constitutional interpretation |
| Implementation | Concrete realization and operational evidence | Authority to define concepts because code exists |
| Organization/deployment | Local authorization, policy, risk, law, and practice | Universalization of local constraints |

## Questions

- What makes a project “SymK-derived” rather than merely inspired by SymK?
- Which artifacts are inherited automatically, and which require explicit adoption?
- Where do organization-specific policies belong?
- How does operational evidence return to challenge higher layers?
- Which incompatibilities invalidate a compatibility claim?
- How are subprojects governed through multiple inheritance levels?

## Expected output

A layer responsibility matrix and placement tests usable in 2.6 when Project Constitutions and Engineering Charters are specified.
