# SymK Markdown Rules

This document defines the **canonical Markdown profile** used by SymK projects.  
All SymK documentation generated by the AI (and edited by humans) **must** follow these rules to ensure:

- Clean diffs and easy Git history
- Predictable conversion to **PDF** and **DOCX**
- Consistent structure across all SymK projects

Markdown (`.md`) is the **source of truth**. PDF, DOCX, HTML and others are **views** derived from it.

---

## 1. File Scope and Purpose

Each `.md` file should represent **one coherent unit**:

- A chapter or section of the Product Life Cycle (PLC),
- A specification document (e.g. `1.1_Product_Vision`),
- A white paper or internal technical note.

Do **not** mix unrelated topics in the same file.

---

## 2. Front Matter (Optional but Recommended)

When the document has a clear title (almost always), use **YAML front matter** at the top:

```yaml
---
title: "SymK Product Designer's Manual"
subtitle: "Phase 1 — Discovery"
author: "Teotoniio Fontana"
version: "v1.3-draft"
date: "2025-12-02"
toc: true
toc-depth: 3
---
```

Rules:

- `title` is mandatory when front matter is present.
- `toc` and `toc-depth` are **hints** for converters (PDF, DOCX).
- Additional fields may be added as needed (`status`, `phase`, etc.), but keep them simple and text-only.

If front matter is missing, tools may fall back to the first `#` heading and filename.

---

## 3. Heading Structure

Headings define the **logical outline** and drive TOCs and PDF bookmarks.

- `#` — Document title  
  - Used once per file, at the very top (after front matter).
- `##` — Major sections (chapters)  
  - Example: `## 1. Purpose`, `## 2. Scope`.
- `###` — Subsections  
  - Example: `### 1.1 Product Vision`, `### 1.2 Problem & Opportunity`.
- `####` — Sub-subsections (use sparingly).

Avoid going deeper than `####`. If you feel the urge for `#####`, split the file.

Headings should be **clear and numbered** when they belong to PLC chapters, e.g.:

```md
## 1. Purpose
### 1.1 Product Vision
### 1.2 Problem & Opportunity
```

---

## 4. Basic Text Formatting

Allowed and recommended:

- **Bold**: `**important**`
- *Italic*: `*emphasis*`
- `code`: backticks for inline identifiers or flags (`--config`, `discover_environment`)
- ~~Strikethrough~~ is allowed but should be rare, mainly to mark deprecated items in drafts.

Avoid HTML tags for styling; keep it pure Markdown whenever possible.

---

## 5. Lists

### 5.1. Unordered Lists

Use a single `-` for list items:

```md
- Primary bullet
- Another point
  - One level of nesting
    - Second level (avoid going deeper)
```

Guidelines:

- Prefer **one level** of nesting, maximum two.
- Keep items short; long paragraphs belong as normal text.

### 5.2. Ordered Lists

For clear sequences of steps:

```md
1. Initialize the environment.
2. Run the orchestrator.
3. Review the logs.
```

Do not rely on “smart” renumbering in some editors; converters will renumber automatically, but the source should still look sane.

---

## 6. Blockquotes

Use blockquotes to highlight notes, warnings or remarks:

```md
> NOTE: This step is optional in proof-of-concept projects.
```

You can prefix the first word with `NOTE:`, `WARNING:`, `TIP:` to signal intent.  
Avoid nested blockquotes.

---

## 7. Tables

Use standard pipe-style tables:

```md
| Phase | Output                 | Status  |
|-------|------------------------|---------|
| 1.1   | Product Vision         | Draft   |
| 1.2   | Problem & Opportunity  | Final   |
```

Rules:

- Always include a **header row** and a **separator row**.
- Alignments (`:---`, `:---:`) are optional; keep them simple.
- No nested tables or complicated layouts; if a table is too complex, split it.

---

## 8. Code Blocks and Logs

Code and console examples are first-class citizens in SymK docs.

Always use **fenced code blocks** with a language when possible:

```md
```python
def discover_environment(cfg, logger):
    logger.info("=== Phase 0: AWS Account + Region Discovery ===")
    ...
```
```

```md
```bash
python3 orchestrator.py --config ./cfg/audit.yaml
```
```

```md
```json
{
  "profile": "default",
  "region": "us-east-1"
}
```
```

```md
```yaml
profile: default
region: us-east-1
```
```

```md
```text
2025-11-09 22:53:58 | backup_orchestrator | INFO | Phase 0.1 AccountIdentity...
```
```

Recommended language tags:

- `python`, `bash`, `sh`, `json`, `yaml`, `ini`, `sql`, `text`

Use `text` for logs, generic console output and anything that is not real code.

No indentation tricks, no mixing of tabs and spaces inside code blocks. What you see is what you get.

---

## 9. Links and Cross-References

Links to external resources:

```md
For details, see the AWS Well-Architected documentation.
```

(If you need the URL, use standard Markdown `[text](url)`.)

Internal references should prefer named sections:

```md
See section [1.1 Product Vision](#11-product-vision) for background.
```

Use the **heading text transformed to an anchor** (lowercase, spaces to dashes). Tools may generate anchors automatically; this convention makes it predictable.

---

## 10. Images

Images are allowed when they add real value (diagrams, PLC overviews, architecture):

```md
![SymK PLC Overview](figures/plc_overview.png)
```

Rules:

- Use relative paths inside the repository (e.g. `figures/...`).
- Prefer `.png` or `.svg`.
- Always supply an alt text in brackets.

Avoid huge screenshots and decorative images that do not support the text.

---

## 11. File Naming Conventions

File names should be:

- **Predictable**,
- **Sortable**,
- **Compatible** with filesystem and tooling.

Examples:

- `1.1_Product_Vision.md`
- `1.2_Problem_Opportunity.md`
- `Whitepaper_IaaC_Executive_Brief.md`
- `SymK_Markdown_Rules.md`

Use underscores `_` instead of spaces.  

For PLC folders, follow the agreed tree (e.g. `PLC/1_Discovery/1.1_Product_Vision.md`).

---

## 12. SymK-Specific Conventions

Because SymK documents are often turned into structured outputs (PDF, DOCX, etc.), the following are **strongly recommended**:

1. **One top-level `#` heading per file** (document title).
2. **Consistent numbering** in headings for PLC content:
   - `## 1. Purpose`
   - `### 1.1 Product Vision`
   - `### 1.2 Problem & Opportunity`
3. **Descriptive section titles**, not generic labels like “Discussion” or “Misc”.
4. **Stable anchors**: once a heading is agreed, avoid renaming it frivolously, as anchors and references may depend on it.

---

## 13. Compatibility With Tools

These rules are designed to be compatible with:

- **MD → PDF** conversion via Pandoc + LaTeX,
- **MD → DOCX** conversion via Pandoc or custom tooling,
- Static-site generators or other Markdown consumers if needed.

The more strictly these rules are followed, the more reliable and “push-button” the conversion workflows become.

---

## 14. Deviations and Extensions

If a document genuinely needs something outside these rules:

- Prefer minimal extensions (e.g. one custom HTML block) over rewriting the document style.
- Document the deviation in a short comment near the top:

```md
> NOTE: This document uses an embedded HTML block for a special diagram.
```

If patterns repeat and prove useful, they can be promoted into future versions of these rules.
